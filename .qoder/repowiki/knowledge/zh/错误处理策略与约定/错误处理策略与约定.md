本仓库采用**分散式 try/except + 结构化 JSON errcode/errmsg 响应**的错误处理模式，未定义统一的异常类型或全局中间件。具体表现如下：

1. **Web 层（main.py）**
   - `/api/chat` 接口使用 `try/except Exception` 捕获所有异常，记录 `logger.error(..., exc_info=True)` 后返回 `JSONResponse(status_code=500, content={"errcode": 500, "errmsg": str(e)})`。
   - `/dingtalk/webhook` 回调对签名校验失败直接返回 `status_code=403, {"errcode": 40001, "errmsg": "签名校验失败"}`；智能体调用异常仅记录日志并将错误信息拼接进回复文本，不中断流程。
   - 空输入等参数校验通过提前 `return JSONResponse(content={"errcode": 1, "errmsg": "empty input"})` 返回，无 HTTP 状态码设置（默认 200）。

2. **Agent 节点层（agent/nodes.py）**
   - 每个可能失败的节点（LLM 路由、RAG 检索、记忆加载、生成回答、记忆更新）均包裹 `try/except Exception`，失败时打印 `[route]/[retrieve]/[memory]/[generate]` 前缀的日志，并返回降级值（空字符串、兜底关键词判断、友好提示文案），保证工作流继续执行。

3. **钉钉客户端层（dingtalk/client.py）**
   - 网络请求统一用 `try/except Exception` 捕获，失败时 `logger.error(...)` 并返回 `{"errcode": -1, "errmsg": str(e)}` 或空字符串/False 等 falsy 值，由上层判断是否降级。
   - access_token 获取失败返回空串，消息发送失败返回 `-1` 错误码，均由调用方决定后续行为。

4. **REPL 调试模式**
   - 用户输入异常（EOFError、KeyboardInterrupt）被捕获并优雅退出；LLM 调用异常仅打印 `[错误] ...` 不影响交互循环。

**约定与约束**
- 所有外部依赖（LLM、HTTP 请求、数据库）均使用最内层 try/except 就近捕获，不向上抛出。
- 对外 API 统一使用 `{"errcode": <数字>, "errmsg": <字符串>}` 结构，成功为 0，业务错误为正数，系统异常为负数或 500。
- 无自定义 Exception/Error 类，无全局异常处理器，无 FastAPI 异常中间件，无 panic/recover 机制。
- 错误信息通过 Python logging 输出到控制台，未集成结构化日志或告警系统。
